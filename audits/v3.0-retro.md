# Umami v3.0 — Architectural Retro

**Date:** 2026-05-13
**Branch:** `v3-restructure`
**Scope:** Architectural reframe in two passes — (1) single-file core → landing + 4 concern-based companion files; (2) flat repo root → `core/` and `ext/` directory layout with deprecation stubs at pre-v3 paths.

This retro captures the v3.0 architectural decision and the rationale behind the concern boundaries. Per §8 retro discipline: a point-in-time record of *what was decided and why*, frozen at the moment of decision so future contributors can read the original reasoning instead of reconstructing it from artifacts.

## What changed

`umami.md` v2.1 was a 2,800-line monolith covering §0–§15, with extensions and shared+variant clusters flat at the repo root and in two ad hoc subdirs (`cms/`, `desktop/`). Adopters on Pro plans or other lower-token-budget providers paid ~40K tokens for every audit / init fetch, most of which was wasted if the project was at Tier 1 / Foundation. The flat repo root also had no visual separation between core and extensions — every file looked the same at a glance.

v3.0 made two architectural moves:

### Move 1 — Split the monolith into landing + 4 core companions

| File | Sections | Purpose |
|---|---|---|
| `umami.md` (landing) | §0, §1, §3b, §6, §13, §15 + Section Navigation Map + Security Essentials sidebar | Framework + Tier 1 practices + navigation. Always fetched. ~13K tokens. |
| `core/umami-quality.md` | §2, §3, §3c, §3d, §3e | Specs, multi-layer testing, decision planning, code review, refactoring |
| `core/umami-runtime.md` | §4, §5, §6b | Runtime validation, full security discipline, threat modeling, trust posture, state recovery, pipeline health |
| `core/umami-process.md` | §7, §8, §10, §12 | Documentation, gap registry + retros + dropped-item audit, change propagation, change tracking |
| `core/umami-agents.md` | §9, §11, §14 | Token efficiency, file size budgets, agent orchestration |

### Move 2 — Reorganize the repo into `core/`, `ext/`, and `recipes/`

The flat repo root was reorganized into four tiers:

- **Root**: `umami.md` (landing — never moves), `README.md`, `CLAUDE.md`, `LICENSE`.
- **`core/`**: the four companion files above.
- **`ext/`**: domain extensions (`umami-web.md`, `umami-data.md`, etc.). Shared+variant clusters live as subdirs under `ext/`: `ext/cms/` and `ext/desktop/` (the existing `cms/` and `desktop/` consolidated under `ext/`).
- **`recipes/`**: drop-in implementation artifacts for cross-cutting features. Distinct from extensions: extensions guide *what to think about*, recipes provide *what to type / copy*. Seeded in v3.0 with `recipes/README.md` (concept + roadmap) and a `consulting-timesheet.md` placeholder. Independent of §0–§30 numbering.

**Deprecation stubs at pre-v3 paths.** Every file that moved (14 pre-v3 paths) has a short stub at its old location. The stub points readers back to `umami.md` for the current Section Navigation Map and notes that the stub will be removed in v3.1. This gives existing adopters a self-discovering migration path rather than a 404.

**Section numbers are stable across files.** Every cross-reference uses `§N` notation; the file location is metadata. Downstream projects' CLAUDE.md files keep working because the landing document is still `umami.md` at the root — the agent reads the Navigation Map and dispatches further fetches. Adopters who already reference `core/` or `ext/` paths get the new files directly; adopters still on pre-v3 paths hit a stub that nudges them to the landing.

## Why this architecture, not the alternatives

The gap registry (entry now superseded) had pre-staged the §0 split as the default seam, with three alternatives:

- **(a) Extract only the §0.6 anti-pattern table** — surgical, but doesn't address the broader cost problem
- **(b) Extract §14 cluster** (~700 lines of orchestration / modes / delegation / model routing / skills / gates / hooks) into `umami-agent-orchestration.md`
- **(c) Extract §3 family** (§3/§3b/§3c/§3d/§3e, ~700 lines of testing / dev / decisions / review / refactoring) into `umami-dev-discipline.md`

The v3 reframe (which inverts the question entirely — keep §0 + Tier 1 *in* landing, move Tier 2+ *out*) was driven by a different framing question:

> If we know enough now to make this a real long-term viable project, what's the right structure?

That changed the answer. Single-companion-file splits (a/b/c) each address one boundary; the deep file would grow back to today's size within 6–12 months and we'd be doing the restructure again. **Concern-based split chosen explicitly for long-term scalability**, with each concern file able to grow in its own lane without hitting the read-truncation problem.

Considered and rejected:

- **Option A (one companion file: `umami-deep.md`)** — captures most of the cost benefit (~67% on Tier 1 fetches) with minimal restructure, but `umami-deep.md` would grow back to monolithic size and force a future restructure. The argument for v3: "if we're doing this restructure once, do it for the long term."
- **5-file split (separate landing + 4 companions)** — chosen.
- **Top-down rewrite** — never seriously considered; section numbers had to stay stable for downstream compatibility.

## Concern boundary rationale

Each section was assigned to a file based on its **primary concern**, not strict tier level. The decision points were:

| § | File | Why this concern, not another |
|---|---|---|
| §2 Specs | quality | Specs define the correctness contract |
| §3 testing family | quality | Testing is the correctness verification mechanism |
| §3c Decision Planning | quality | Design correctness — "did we make decisions deliberately?" |
| §3d Code Review | quality | Correctness verification at PR boundary |
| §3e Refactoring | quality | Preserving correctness during structural change |
| §4 Runtime Validation | runtime | Production correctness + the security stack lives here |
| §5 State Recovery | runtime | Operational survivability |
| §6b Pipeline Health | runtime | DevOps pipeline is operational substrate |
| §7 Documentation | process | Project meta — how the project explains itself |
| §8 Gaps & retros | process | Process learning artifacts |
| §10 Change Propagation | process | How changes coordinate across files |
| §12 Change Tracking | process | Session handoff is process discipline |
| §9 Token Efficiency | agents | Agent-context-cost concern |
| §11 File Size Budgets | agents | About agent context, not general code quality |
| §14 Agent Orchestration | agents | Obvious |

Edge cases resolved:

- **§11 File Size Budgets in agents (not quality)** — the trigger per §0.6 Tier 2 is "files long enough that agents truncate or miss context". The concern is agent-context-shaped, not code-quality-shaped.
- **§6b Pipeline Health in runtime (not quality)** — pipeline is the operational substrate; cycle-time and gate dispositions are ops concerns.
- **§4 stays whole in runtime** — splitting §4 across files (Tier 1 floor in landing, deep in runtime) was rejected; instead a **Security Essentials sidebar** in the landing carries the day-one floor (~30 lines: no secrets, scan deps, parameterize queries, basic auth, build hygiene) with explicit pointer to §4 for full treatment.

## What the Section Navigation Map does

The landing carries a new top-level table mapping every § to its file, its tier, and its fetch trigger. This is the **canonical index** that the agent consults before fetching companion files. It replaces the implicit "read everything" pattern of v2.

Format:

```
| § | Topic | File | Tier | Fetch when... |
```

When sections move between files in the future, the Map is the single source of truth that must be updated in lockstep with the move (per CLAUDE.md Change Propagation Map).

## Cost math, validated

| Adoption path | v2 (40K-token monolith) | v3 (split) | Reduction |
|---|---|---|---|
| Tier 1 / brand new project | ~40K | ~13K | **67%** |
| Tier 2 testing-heavy project | ~40K | 13K + 9K = 22K | 45% |
| Tier 2 agent-orchestration project | ~40K | 13K + 6K = 19K | 52% |
| Tier 3 mature project, full umami | ~40K | 13K + 9K + 8K + 5K + 6K = 41K (across files, rarely all at once) | similar |
| Audit Tier 1 project | ~40K every audit | ~13K every audit | **67%** |

Most adopters fall into Tier 1 or single-concern Tier 2 — both benefit substantially. Mature Tier 3 projects pay similar total cost, but distributed across multiple targeted fetches rather than one monolithic load.

## Implementation cost

About one focused session: 4 companion files created, landing slimmed and augmented with Navigation Map + Security Essentials, cross-references audited, §0.7 and §0.7b protocols updated for split-aware fetch, README updated extensively, CLAUDE.md Files table and Change Propagation Map updated, skill files re-synced (`umami-audit.md`, `umami-init.md` to 2026-05-13).

## Risks accepted

| Risk | Mitigation |
|---|---|
| Wrong concern boundary becomes permanent (because §N is stable) | The boundary rationale table above is the explicit decision record. If a boundary proves wrong, a future restructure relocates the section but cross-refs survive because they use `§N`, not paths. |
| Navigation Map drift from actual section locations | New §15 checklist item (planned): "if you move a section between files, update Navigation Map"; future fitness function candidate. |
| Cross-file refs go stale | §3d code review discipline should flag cross-file `§N` refs that lack file hints (currently optional, may become required). |
| Adopter confusion about which file to fetch | Section Navigation Map is THE answer; README explains; init/audit skills handle dispatch automatically. |
| Five files feels like more to maintain | Concern boundaries mean each file is edited independently by topic; merge-conflict surface area decreases vs. monolithic umami.md. |
| Downstream projects' CLAUDE.md files break | They don't — umami.md is still the entry point; agent uses Navigation Map to dispatch. |

## Backwards compatibility guarantees

- **Existing project CLAUDE.md files don't break.** They reference `umami.md` → still works → agent reads landing → uses Navigation Map → fetches companion files when needed.
- **Section numbers stay stable.** A downstream `§3d` reference still resolves to §3d (now in `umami-quality.md`).
- **The bootstrap one-liner still names `umami.md`.** No URL changes for adopters.
- **Cross-file `§N` notation works.** Documented explicitly in CLAUDE.md's Change Propagation Map: section number is the stable identifier; file location is metadata.

**Known break:** Anyone who previously fetched and cached `umami.md` and relied on having all sections in one document needs to also fetch companion files. The §0.7 protocol's existing "never cache locally" guidance protects against this — adopters following the protocol fetch fresh and use the Navigation Map.

## What to validate post-merge

Per the new gap-registry entry "v3 multi-file architecture not yet validated at scale by external adopters":

1. First external adopter bootstrapping a fresh project via the one-liner — does the landing-alone Tier 1 fetch deliver enough discovery information?
2. Does the agent correctly use the Section Navigation Map to dispatch companion fetches when escalation triggers?
3. Refine Navigation Map / Security Essentials sidebar based on what surfaces in the first few real adoptions.

## v3.1 follow-up plans (documented up front, not deferred-to-forget)

Three explicit follow-ups for v3.1:

1. **Remove all v3.0 deprecation stubs.** The 14 stubs at pre-v3 paths (`umami-web.md` at root, `cms/umami-wordpress.md`, etc.) exist for the v3.0 grace period only. v3.1 removes them; legacy paths 404 from that point forward.
2. **Roll up §20 (WordPress) and §21 (Drupal) into §25 (CMS).** The `ext/cms/umami-wordpress.md` and `ext/cms/umami-drupal.md` files will be removed entirely; their content folds into `ext/cms/umami-cms.md`. This was already pre-staged in the gap registry; v3.1 executes it. Section numbers §20 and §21 remain reserved but unused (no renumbering).
3. **Validate v3 architecture against external adopters.** The gap-registry entry "v3 multi-file architecture not yet validated at scale by external adopters" tracks the field-validation work. v3.1 lands refinements based on what surfaces during the v3.0 release window.

## Closing
